## 1. テスト方針

### 1.1 目的

- 生徒の7画面と管理者の2画面が、設計どおり動くことを確認する。
- 理念が守られていることを確認する。AI が断定しない。職業に文理ラベルを付けない。生徒の個人情報を AI に送らない。
- 講師要件（MUST）の「単体テストのコード」と「テスト設計書・テストシナリオ」を満たす。

### 1.2 範囲

| 区分 | 対象 |
| ---- | ---- |
| バックエンド | マッチング、診断 API、職業 API、マスタ、生徒セッション、管理者認証、学校・契約、決済（Checkout・Webhook）、AI 出力の検証、キャッシュ、レート制限、共通エラー |
| フロント | 生徒7画面と管理者2画面（手動で確認） |
| 非機能 | セキュリティ（認可、入力検証、XSS）、スマホでの表示と操作、AI 失敗時のフォールバック、Redis 障害時の継続 |

### 1.3 実施しないもの

| 項目 | 理由 |
| ---- | ---- |
| フロントの自動テスト（Playwright） | 工数を生徒画面に集中するため。手動シナリオで代替 |
| 負荷試験 | 時間がないため。同時200人・95%が1秒以内は目標値のまま未検証 |
| 実施しない機能のテスト | 「知らなかった！」、結果の再表示・共有、契約切れの生徒制限は実装していない |
| 外部サービス本体 | Stripe・Firebase・OpenRouter は自動テストではモック |
| 詳細な性能・脆弱性診断 | OWASP 対応は設計とレビューで担保 |

## 4. 合否基準

| 区分 | 基準 |
| ---- | ---- |
| 自動テスト | `pnpm test` で全件合格（失敗・スキップ 0）。lint・format・build も成功 |
| 手動テスト | 手順どおりに操作し、期待結果と一致したら ○。違えば ×（不具合として記録）。実施できなければ「未実施」と理由を書く |
| 全体 | 全シナリオが ○。× は修正して再テストし ○ になること |

画面の「完成の定義」は [`画面設計`](./画面設計.md) §1.5 に従う。

### 不具合の重大度

| 重大度 | 例 | 扱い |
| ------ | -- | ---- |
| 高 | 診断が通らない、決済が反映されない、他校のデータが見える、個人情報の漏えい、画面のマージンが取れていない（内容が切れる・端に張りつく） | 修正しないとリリース不可 |
| 中 | 画面の崩れ、文言の断定、エラー表示の誤り | 原則修正。しない場合は理由を記録 |
| 低 | 軽微な見た目・文言、画像・アイコンが世界観に合っていない | 余裕があれば修正 |

## 5. 自動テストと設計の対応

| 観点 | テストファイル | 確認している設計 |
| ---- | -------------- | ---------------- |
| マッチング | `matching`、`whyConnected` | 上位3つ、同数は sort_order、×3+×2、上位10件、同点は職業ID順 |
| 診断 API | `diagnoses` | 401、入力検証（0/4個、重複、不在、他質問の選択肢）、201、AI 文の保存、AI に渡す内容 |
| 職業・マスタ | `jobs`、`masters` | 400/404、API設計 §3.6 の形、文理は学問にのみ、Redis 1時間、Redis 障害時 |
| AI | `strengthAi`、`strengthCache` | 断定語・文字数・文字化け・途中切れの検査、固定文への置換、24時間キャッシュ |
| 生徒の認証 | `studentSession`、`requireStudent` | 201、404、SECRET 未設定、学校ID不一致 |
| 管理者の認証 | `requireAdmin`、`me` | 401・403・500 の分岐、偽ロール、期限切れ |
| 学校・契約 | `schools`、`contractStatus` | 4状態の返却、他校を指定しても自校のみ、Stripe ID を返さない |
| 決済 | `billing`、`billing.app` | 409 重複、署名検証、冪等、1年後（2/29）、Stripe エラーを隠す |
| 基盤 | `rateLimit`、`cache`、`redis`、`trustProxy`、`validate`、`errors`、`health` | 429・Retry-After、Redis 障害時は制限なし、共通エラー形式 |
