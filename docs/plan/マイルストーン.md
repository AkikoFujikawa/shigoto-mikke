# マイルストーン・スケジュール（チームC・5名／締切 2026-10-18）

> **最優先は「生徒画面をきちんと作り上げること」。** それ以外は、生徒画面の完成を邪魔しない範囲で最小限にする。
> 講師指定のレビュー日が決まっていれば差し替える。以下は締切から逆算した仮置き（コードフリーズは **10/16(金)**）。

## 方針

| 優先 | 内容 |
| ---- | ---- |
| **P0（第一）** | **生徒画面の完成度**：7画面（入口・カード・5問・強みのタネ・職業スワイプ・職業詳細・共通エラー）が、スマホ実機で迷わず・気持ちよく使えること。ローディング／エラー／文言／見た目／アクセシビリティまで含めて完成させる |
| P1（講師要件の最小実装） | 管理者3画面＋Stripe（テストモード・最小）、Docker、Redis（職業マスタのキャッシュのみ）、XSS／SQLi対策、単体テスト、テスト設計書、ログ出し分け、**本番デプロイ（HTTPS。提供ドメインでよい）**、LLM（結果画面の中核として P0 の一部） |
| **実施しない** | サブドメイン取得、フロント自動テスト（Playwright）、`openapi.yaml`、「知らなかった！」、結果の再表示・履歴、結果共有、契約切れの生徒制限、マッチングの分野分散、診断の細かいレート制限（AIの上限は最小限） |
| データ | 職業は**現在39件（タグ・学問との対応は完成）**。残りは**画面向けの文言の仕上げ**と**画像（AI制作中）**。全12タグに2件以上あることを守る。画像・文言が間に合わない職業は絵文字＋短文で表示し、デモ用の職業（各タグの代表）から先に仕上げる |

## 5名の担当（案）

生徒画面に**3名**（A・B・C）を充てる。

| 担当 | 主な役割 |
| ---- | -------- |
| A | 生徒フロント前半：入口（登録）・好きなもの・5問・強みのタネ。**デザインの統一（共通コンポーネント）** |
| B | 生徒フロント後半：職業スワイプ・職業詳細・共通エラー。Week3 に管理者フロント3画面 |
| C | バックエンド（生徒体験）：認証・診断API・マッチング・AI連携・フォールバック |
| D | バックエンド（基盤）：DB／seed、マスタ・職業API、Redis、Stripe・契約、**Docker・CI・本番デプロイ** |
| E | データ準備（職業データの仕上げ・文言（画像はAI制作の担当者が対応））、**テスト設計書・シナリオ**、スライド。各自の単体テストの取りまとめ |

- 各自が**自分のコードの単体テストを書く**（マッチング、入力検証、契約判定、AI出力の検証）。
- データ準備は E が主担当。ただし **職業文言のレビューは A・B も参加**（画面に出る文言の品質のため）。

### 余力に収めるための選択肢（Week1 の初日に決める）

| 案 | 内容 | 効果 |
| -- | ---- | ---- |
| A. 稼働を増やす | 平日2h＋土日4h（週18h・4週間で72h） | 余力が約45人日になり、上の約40人日が収まる（余裕は約1割） |
| B. 講師に確認する | MUST の最小実装で足りるか（Redis はマスタのキャッシュのみ、Stripe はテストモードの Checkout まで、テスト設計書は4本）を確認 | 約4人日は確実に短縮 |
| C. さらに絞る | 生徒画面を減らす、5問を3問にする、管理者を1画面にする | 生徒画面の完成度と企画の質が下がる（非推奨） |

**推奨：A と B の併用。** 生徒画面の完成度を守るため、C は避ける。
上の見積もりには、現在の設計書と異なる**案**が含まれる（「なぜつながる？」を AI ではなくタグから作る定型文にする／学校の自己登録画面を作らず学校は seed で作成する／フロントを Docker に入れない）。**採用する場合は、チームで決めてから設計書を更新する**。

## 削る順（工数が足りなくなったら）

1. 管理者画面の見た目の作り込み（機能だけ動けばよい）
2. Redis は「マスタのキャッシュ」だけにする（AI結果のキャッシュはやらない）
3. 文言を仕上げる職業を25件に絞る（残りは絵文字＋短文で表示。全12タグ×2件は維持）
4. 単体テストはマッチング・入力検証・契約判定の3種類に絞る
5. テストシナリオは「生徒フロー」「管理者フロー」「決済」「エラー系」の4本に絞る

**削らないもの**：生徒画面の7画面、スマホ実機確認、AIのフォールバック（失敗しても画面が壊れない）、本番デプロイ。
