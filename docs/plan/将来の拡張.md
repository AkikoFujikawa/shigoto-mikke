# 将来の拡張（今回の4週間では実施しない）

> 今回は**生徒画面の完成度を最優先**にし、生徒の認証は案B（学校コード＋ニックネーム）の最小構成にした。ここでは、今回やらないことのうち**将来の拡張として検討する内容**と、そのとき困らないように**今の設計で守っておくこと**をまとめる。
> 工数は 1人日＝8時間の目安（案Bとの差分）。

## 1. 学校向けの集計・生徒の特定

学校の課題（生徒一人ひとりの興味・関心に合わせた進路支援）に応えるための拡張。

### 1.1 段階と選択肢

| 段階 | 内容 | できること | 追加工数 |
| ---- | ---- | ---------- | -------- |
| **① 匿名の集計** | 診断を学校単位で集計し、管理画面に表示 | 診断した生徒数、人気の好きなもの Top3、多く見られた職業、強みの分布 | 約 +3 |
| **② クラス別の集計** | 入口に「クラス」の選択を追加（任意） | クラス別の傾向（個人は特定しない） | ①に約 +1 |
| **③ 個人の特定** | 学校が生徒を識別できる仕組みを導入 | 生徒ごとの結果を学校が把握（個別面談での活用など） | 下表 |

### 1.2 個人を特定する方式の比較

| 方式 | 内容 | 追加工数 | 利点 | 課題 |
| ---- | ---- | -------- | ---- | ---- |
| **A：メール登録（Firebase）** | 生徒がメールで登録。氏名・クラスも入力 | 約 +9 | 別端末で結果を見返せる | 個人情報を預かる。**メールだけでは学校のどの生徒か分からない**（氏名・クラスの入力が別途必要） |
| **Google ログイン（学校のアカウント）** | Firebase の Google 認証で学校のアカウントでログイン | 約 +8 | パスワード管理が不要。学校のドメインで生徒を識別できる | 学校側で外部アプリの許可が必要な場合がある |
| **学校が生徒 ID＋PIN を配る** | 管理者が生徒を登録（CSV 等）し、生徒は ID と PIN で入る | 約 +11 | 学校が識別子を握るので特定に最も向く | 実装量が最大。学校の運用負荷 |

**推奨（次のフェーズ）**：**①匿名の集計 → ②クラス別 → ③個人の特定（学校 Google アカウント、または学校が ID と PIN を配る方式）** の順に進める。個人の特定は、メール登録（A）ではなく、**学校が生徒を管理する運用になじむ方式**を選ぶ。

### 1.3 個人を特定する前に決めること（実装より先）

| 項目 | 内容 |
| ---- | ---- |
| 個人情報の扱い | 未成年の情報を預かる。保存する項目・保存期間・削除方法を決める |
| 同意 | 保護者・学校の同意の取り方（利用規約・プライバシーポリシー） |
| 学校との役割分担 | 生徒の識別情報（氏名・出席番号）を、学校が持つのか、システムが持つのか |
| データの見せ方 | 教員が個人の結果を見てよい範囲（結果の扱いが「決めつけ」にならないための注意書き） |
| 理念との整合 | 「AIは向いている・向いていないを決めない」理念を、個人の結果画面でも守る |

## 3. 拡張しやすくするために、今の設計で守っておくこと

| 守ること | 理由 |
| -------- | ---- |
| **`students` に `school_id` を持たせ、診断は `students` に紐づけて保存する**（現在の設計） | 学校単位の集計が、データの作り直しなしでできる |
| **`interests`／`traits`／`jobs` の `code`（ID）を変更しない** | 過去の診断データとの対応を保つ（集計が壊れない） |
| **生徒（`students`）は作成から30日で削除され、診断も連動して消える**（現在の設計）。集計を導入する際は、**削除期間を延ばす、または集計値を別テーブルに残してから削除する** | 削除された診断は集計できない。匿名集計を始める前に必ず見直す |
| **`diagnoses` に入力（選んだ好きなもの・回答）と結果（強み・職業候補）を保存する** | 後から集計できる。**保存しない構成にすると、集計の拡張ができなくなる** |
| **生徒の識別子は `students.id`（内部ID）だけに依存させる** | 認証方式を将来変えても（ニックネーム→ID＋PIN など）、診断データを引き継げる |
| **認証はミドルウェアで分離する**（生徒／管理者でトークンの種類が別） | 生徒側の認証方式を差し替えても、他のコードに影響しない |
| **ニックネームを画面や API で「識別」に使わない** | 重複を許す前提のため。個人の特定には別の識別子を追加する |
| **AI に個人情報（ニックネーム・学校名など）を送らない** | 個人の特定を導入しても、AI 側に個人情報が渡らない |

> **重要**：診断結果の保存を省く案（工数削減のため）を採る場合、①匿名の集計ができなくなる。学校向けの価値（集計）を将来提供したいなら、**診断の保存は残す**方がよい。

## 4. 拡張の進め方（案）

1. **フェーズ1（今回）**：生徒画面の完成度、案Bの最小構成、MUST の最小実装。
2. **フェーズ2**：①匿名の集計（管理画面に1〜2カード）、「知らなかった！」、レート制限。
3. **フェーズ3**：②クラス別の集計、③個人の特定（方式の選定・同意の整備から）、結果の再表示。
4. **フェーズ4**：結果の共有、「次の行動」、ロードマップ、自己登録の承認制。

学校への導入を進める場合は、**フェーズ2（匿名の集計）を最初の付加価値**として提案すると、個人情報の問題なしに、学校の課題（進路支援の手段の不足）に応えられる。
