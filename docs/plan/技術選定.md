# 技術選定

## 1. 選定方針

優先順位（上ほど優先）：

1. **4週間で完成できること**（学習コスト・情報量・チームの習熟度）
2. **カリキュラム要件を満たすこと**（フロント→API→DB接続、API/DB設計を成果物にできる構成）
3. **無料〜低コストで運用できること**（無料体験・デモ段階）
4. **授業中の一斉アクセスとAI呼び出しに耐えること**
5. 未成年の個人情報を扱うため、**セキュリティ・データの持ち方を自分たちで説明できること**

> 前提：5名・締切2026-10-18。5名で並行開発するため、フロント／バックを分離し、API設計書（`docs/plan/API設計.md`）を先に固めて担当を分けやすくする。チームの得意言語は要確認。ここでは `テンプレート/README.md` の想定（TypeScript／Express or NestJS／Prisma／PostgreSQL）と、既存のExpress+TSのAPI実装経験を前提に「習熟度重視」で選ぶ。

## 2. 技術スタック一覧

| レイヤ | 採用技術 | 候補 | 選定理由 |
| ------ | -------- | ---- | -------- |
| 言語 | TypeScript（フロント・バック共通） | JavaScript | 型でデータの取り違えを実装前に検出でき、手戻りを減らせる |
| フロントエンド | **Next.js（React）＋ Tailwind CSS**。生徒UIはスマホファースト、管理画面はPC向けレイアウト | Vite+React、Vue/Nuxt | 1つのアプリで生徒（スマホ）と管理者（PC）を出し分けやすい。情報量が多い。スワイプは CSS scroll-snap（追加ライブラリ不要）または Framer Motion。Vercel に無料でデプロイ可 |
| バックエンド | **Express（TypeScript）＋ express-validator（入力検証）** | NestJS、Next.js API Routes、Hono | テンプレート想定と一致し、既存経験を活かせる。NestJSは学習コストが高く4週間では過剰。API Routesは「フロント→API→DB」の分離が見えにくい |
| ORM / マイグレーション | **Prisma** | TypeORM、Drizzle | スキーマ＝DB設計書として使え、seed・マイグレーションが簡単。型が自動生成される |
| データベース | **PostgreSQL**（Neon または Supabase の無料枠） | MySQL、SQLite、Firestore | 職業↔タグ↔学問領域の多対多を素直に表現できる。リレーショナルなのでDB設計の成果物に向く。認証は Firebase Auth を使い、DB は Firestore ではなく PostgreSQL とする |
| 認証 | **学校管理者：Firebase Authentication（メール＋パスワード）**（Express は Admin SDK で ID トークンを検証し、UID から DB の `school_admins` を引く）。**生徒：認証なし（案B）**。学校コード＋ニックネームで `POST /v1/students/session` を呼び、サーバーがセッショントークン（JWT・HS256・有効期限8時間）を発行する。DB は PostgreSQL のまま | 生徒もFirebase（メール登録）、全員自前JWT、Supabase Auth、Auth0、Clerk | 生徒のメール・パスワード・登録／ログイン画面が不要になり、**個人情報を預からず**、生徒画面の工数を確保できる（案Bで約3人日、案Aは約6人日）。管理者は大人で、パスワード管理と再設定メールを Firebase に任せられる。JWT はサーバー側の秘密鍵（`SESSION_SECRET`）で署名し、生徒ID・学校ID・ロールだけを入れる。（**案B：暫定決定**。チーム確認後に確定） |
| AI（生成） | **OpenRouter 経由・`openai/gpt-oss-120b`（コース配布の共有APIキー。チャット5モデル中、入出力とも最安値クラス）** をサーバーからのみ呼び出し。出力は **Structured Outputs（`response_format: json_schema`、`strict: true`）** で構造化。Node.js 公式 SDK（`openai`）の `baseURL` を `https://openrouter.ai/api/v1` に向けて使用（SDKの差し替え不要） | 他の配布モデル（DeepSeek V4 Flash、GLM 4.7 Flash、GPT-5 Nano、Gemma 4 26B A4B）、上位モデル（Claude・GPT-4o等。自己負担・講師相談が必要） | 用途は「強みの言語化」のみで軽量モデルで十分（「なぜつながる？」はタグの一致からテンプレートで組み立て、AIを使わない。#30で決定）。低コスト・低遅延で一斉利用に向く。スキーマ指定で出力形式の逸脱を防ぎ、断定表現の禁止はシステムプロンプトと検証で制御。個人情報は送らない |
| 職業マッチング | **DBのタグ一致スコアリング（アプリ内ロジック）** | 埋め込み検索（ベクトルDB）、LLMに職業を選ばせる | 職業は「あらかじめ登録した中から」提案する要件。決定的で説明可能、コスト0、テストしやすい。LLMに選ばせると「決めつけ」リスクとコスト・遅延が増える |
| 決済 | **Stripe Checkout（テストモード）＋ Webhook** | 請求書払い・手動管理、Paddle | 画面設計どおり独自決済画面を作らず遷移のみ。カード情報を扱わない。Webhookは `checkout.session.completed` のみ実装 |
| 画像 | 職業画像は**AI生成（制作中）**。フロントの `public/jobs/` に静的ファイルとして置き、`jobs.image_url` にパスだけ保持。画像がない職業は絵文字で代替 | Supabase Storage、フリー素材 | ストレージを別に用意せず工数を省ける。仕様は [`画面設計`](./画面設計.md) の「職業画像の仕様」を参照 |
| コンテナ | **Docker**。API・フロント・PostgreSQL・Redis を Docker Compose で一括起動（開発）。**API は本番もコンテナ（Dockerfile）で動かす**。フロントの Dockerfile は**開発用**（Docker Compose に含める）。**本番のフロントは Vercel（コンテナなし）で動かす**（講師確認済み） | コンテナなし | 講師要件（MUST）。開発環境差分を無くし、本番との差も小さくできる |
| キャッシュ | **Redis**（Render Key Value または Upstash の無料枠）。用途は**職業・質問・好きなものマスタのキャッシュのみ**。余裕があれば診断結果のキャッシュ・レート制限を追加 | Memcached | 講師要件（MUST）。最小の使い方で要件を満たし、工数を抑える |
| ホスティング | **フロント：Vercel／バックエンド（Docker）：Render／DB：Neon／Redis：Render Key Value または Upstash**。※本番デプロイ・HTTPS 必須 | Fly.io、Google Cloud Run、AWS | ADVANCED（本番デプロイ）を満たす。いずれも Git 連携デプロイと自動 HTTPS が可能。Render無料枠はスリープあり→デモ前にウォームアップ or 有料最小プラン |
| ドメイン / HTTPS | **独自ドメイン（サブドメイン）は取得しない**。提供ドメイン（`*.vercel.app`／`*.onrender.com`）の自動証明書で HTTPS 化。認証は Authorization ヘッダー（Bearer）で行うため Cookie は使わない | 独自ドメイン＋サブドメイン | 生徒画面に工数を集中するため ADVANCED の「サブドメイン取得」は実施しない（講師に評価範囲を確認） |
| CI / CD | **GitHub Actions**（lint・型チェック・単体テスト）＋ Vercel/Render の Git 連携自動デプロイ | なし（手動） | 数十行で導入でき品質を担保。**Playwright は実施しない** |
| テスト | **単体**：Vitest（マッチングロジック、入力検証、契約判定、AI出力の検証）＋ Supertest（API）。**大枠**：テスト設計書＋テストシナリオ（手動、**スマホ実機を重視**） | Jest、Playwright、Cypress | 講師要件（MUST：単体テストコード、テスト設計書）を満たす。フロント自動化（ADVANCED）は実施しない |
| Lint / Format | ESLint / Prettier | — | テンプレート準拠 |
| 監視・ログ | 構造化ログ（pino）。**環境変数 `NODE_ENV` でログレベル・出力形式を切替**：開発＝debug・整形出力（pino-pretty）、本番＝info以上・JSON、個人情報やトークンはマスク。Render/Vercel のログ、AI呼び出しの所要時間・失敗を出力。Stripe Webhook は Stripe ダッシュボードで確認 | Sentry、Datadog | 講師要件（MUST：環境ごとのログ出し分け）。余裕があれば Sentry 無料枠 |
| API仕様 | **`docs/plan/API設計.md` を仕様とする**（`openapi.yaml` は作成しない） | OpenAPI（Swagger） | 工数を生徒画面に集中する。講師レビューは API設計書で行う |
| 開発環境 | Docker Compose（front / api / PostgreSQL / Redis）、pnpm、`.env.example`（Firebase・Stripe・OpenRouter のキーと `SESSION_SECRET` は環境変数） | — | 環境差分を減らす |

## 3. 比較サマリ

| 論点 | 採用 | 不採用 | 判断根拠 |
| ---- | ---- | ------ | -------- |
| バックエンド | Express | NestJS | 学習・記述量が多く4週間では過剰。レイヤ分割はディレクトリ規約で代替 |
| フロント/バック構成 | 分離（Next.js + Express） | Next.js フルスタック（API Routes） | カリキュラムの「フロント→API→DB」確認と、講師にAPI設計を見せやすい点を優先。講師要件（MUST）で分離が必須のため、フルスタック構成は採用しない。Next.js はフロント専用とし、`app/api` 等の Route Handlers にはビジネスロジックを置かない |
| 認証 | 管理者：Firebase／生徒：認証なし（学校コード＋ニックネームのセッションJWT） | 生徒もメール登録（Firebase）／全員自前JWT | 生徒の個人情報を預からず、生徒画面の工数を確保。管理者の認証は Firebase に任せてセキュリティ実装を減らす |
| 職業選定 | タグスコアリング | LLM選定／ベクトル検索 | 「決めつけない」「登録済み職業から提案」要件、コスト、説明可能性 |
| AI利用範囲 | 強みの言語化のみ（「なぜつながる？」はタグの一致のテンプレートで、AIは使わない。#30で決定） | 職業推薦・チャット | リスクとコストの最小化。企画理念と整合 |
| AIモデル | OpenRouter経由・`openai/gpt-oss-120b`（コース配布の共有APIキー） | 他の配布モデル／上位モデル（自己負担） | 短文生成で十分。チャット5モデル中、入出力とも最安値クラス。一斉利用時の遅延・コストを抑制 |
| DB | PostgreSQL | Firestore / SQLite | 多対多のタグ構造・DB設計成果物・本番運用の見通し |
| 決済 | Stripe Checkout | 独自フォーム／手動請求 | カード情報を扱わずセキュアで、実装が最小 |
| 画像 | 静的（public/）、AI生成 | Storage／フリー素材 | 工数削減。AI生成は制作中（決定済み）。利用規約・権利の確認が必要 |

## 4. リスクと対応

| 技術 | 懸念点 | 緩和策 |
| ---- | ------ | ------ |
| OpenRouter（`openai/gpt-oss-120b`） | 遅延・失敗・レート制限（授業で一斉に診断ボタンが押される。コース全体の共有予算のため、他チームの利用状況にも影響される） | タイムアウト（例：15秒）＋自動1回再試行（再試行の回数は、AI 利用の詳細仕様で確定する）。診断結果はDB保存して再生成を防ぐ。IPではなくユーザー単位のレート制限。失敗時は固定文（`traits.description`）にフォールバックし、診断は成功させる（案A）。429（レート制限）は指数バックオフで再試行 |
| OpenRouter（`openai/gpt-oss-120b`） | 不適切・断定的な出力、個人情報の混入 | システムプロンプトで断定禁止、Structured Outputs＋サーバー側でのスキーマ検証、入力は選択肢IDのみ（自由記述なし）で個人情報が入らない設計。**キーを生成AIへ貼り付けない・SNS等へ共有しない**（コース配布キーの注意事項） |
| OpenRouter（`openai/gpt-oss-120b`） | コスト | 1診断あたりの呼び出しは**原則1回**（失敗時の再試行を含めても最大2回）。同じ入力は Redis のキャッシュで再利用。**共有予算のため、月額上限の設定はスクール側の管理**（チームでは設定しない） |
| Firebase Auth（管理者） | 誰でも学校（管理者アカウント）を作れてしまう | 無料体験（30日）のみで、生徒の個人情報は預からないため影響は小さい。問題になった場合は学校の作成を承認制にする（今回は行わない） |
| Firebase Auth × Express | ID トークン検証の実装漏れ、Admin SDK の秘密鍵の環境変数（改行コードの扱い）で詰まる | 検証ミドルウェアを共通化し全保護ルートに適用。学校IDでのクエリ絞り込みも共通化。秘密鍵は Week1 の疎通確認で動作確認する |
| Firebase Auth（管理者） | Google への外部依存、管理者のメールの取り扱い | 管理者（教員）のメールのみ。規約・PPに委託先として記載 |
| 生徒のセッション（JWT） | 学校コードの総当たり・共有による不正利用、トークンの盗用 | 学校コードは推測されにくい英数字6文字。開始APIにIP単位のレート制限（余裕があれば）。トークンは有効期限8時間・`sessionStorage` 保存（タブを閉じると消える）・個人情報を入れない。生徒データにメール・氏名がないため、不正利用の影響は小さい。学校コードの再発行は今回実装しない |
| XSS | 表示データ（職業名、AI生成文）経由のスクリプト混入 | React の自動エスケープに任せ `dangerouslySetInnerHTML` は禁止（ESLint ルール化）。API は JSON のみ返す。CSP・`helmet` 導入。AI 生成文も信頼せずテキストとして表示 |
| SQL インジェクション | 入力値経由の不正クエリ | Prisma のパラメータ化クエリのみ使用。生 SQL（`$queryRaw`）は原則禁止、必要時はタグ付きテンプレートで。express-validator で全入力（body／params／query）をサーバー側で検証。入力検証は express-validator に統一（Zod など他ライブラリは混在させない）。エラー時に400を返す共通ミドルウェアを1つ作り全ルートで使う。検証はルート定義の直前に置き、検証なしのルートを作らない |
| プロンプトインジェクション | 入力を通じた AI への指示混入・システムプロンプト漏えい | **入力は選択肢ID（ホワイトリスト）のみで自由記述なし**。ID は DB のマスタと照合してからプロンプトに文言として埋め込む。システムプロンプトとユーザー由来データを分離し、出力は JSON スキーマで検証（逸脱は破棄→定型文）。出力に URL・命令文が含まれれば除外。将来自由記述を入れる場合は入力長制限・区切り・注意喚起のうえ追加対策 |
| Redis | 障害時に全体が止まる、キャッシュ不整合 | Redis 障害時は DB/AI へフォールバック（キャッシュはあくまで補助）。TTL を設定。職業マスタ更新時はキャッシュを削除 |
| Docker | 本番イメージの肥大・秘密情報の混入 | multi-stage build、`.dockerignore`、キーは環境変数（イメージに含めない）。本番用と開発用で compose を分ける |
| ドメイン / HTTPS | 独自ドメインは取得しないため、提供ドメイン間のオリジン違い（CORS）の設定で詰まる | 提供ドメインの自動証明書を使用。フロントとAPIのオリジン（CORS）を Week1 の疎通確認で確認する |
| Render 無料枠 | スリープで初回アクセスが遅い | デモ前にウォームアップ／最小有料プラン。ヘルスチェックエンドポイント |
| Neon / 無料DB | 接続数・休止・容量 | Prisma のコネクション設定、コールドスタート許容。データ量は小さいため容量は問題なし |
| Stripe | Webhook 検証・契約状態の不整合 | 署名検証、`checkout.session.completed` のみ処理、冪等性（同一イベントの二重処理防止）。テストモードで通し確認 |
| Next.js × Express 分離 | CORS（別オリジン）の設定で詰まる | 早期（Week1）に疎通確認。同一親ドメイン化またはプロキシ（rewrites）で回避 |
| スワイプUI | スマホ実機でのスクロール挙動差（iOS Safari） | CSS scroll-snap を基本にし、Week2でiOS/Android実機確認 |
| チーム習熟度 | 想定スタックに未経験者がいる | Week1 で全員が「ログイン→DB1テーブル取得」を通す。詰まった場合は Week1 末までにペアで解消する（分離は講師要件のためフルスタックへの切替は不可）。Docker Compose の起動確認も Week1 の全員タスクに含める |
| 個人情報（未成年） | 法令・学校の情報セキュリティ基準 | 取得最小化、規約・PP、データ削除方針を決める。学校導入時の説明用にデータ取扱い資料を準備 |
