### 2. プロジェクト概要

- **システム名**：しごとみっけ
- **システムの目的・背景**：
  - 文理選択前の高校1年生が「好きなこと・得意・価値観」を入力し、AIによる整理をもとに、あらかじめ登録された職業から自分の強みに関連する職業に出会えるWebアプリ。
  - 気になった職業について、仕事内容に加えて「関連する学問」と「文系／理系／複合」のつながりまで確認できる。
  - **AIは「この職業に向いている」「理系にすべき」と決めない。** 知らなかった職業との出会いを作り、文理選択・進路を本人が考える材料を増やすことが目的。
  - 学校経由で提供し、30日間の無料体験後に学校単位で有料契約するモデルを想定。
- **関係者**：
  - 講師：（記入）
  - 開発チーム：チームC（5名。役割分担は記入）
  - 利用者（生徒）：高校1年生（ペルソナ：美咲さん）。スマホで利用
  - 利用者（学校管理者）：教員等。PCで利用
  - 間接的な関係者（親）：アプリの直接利用者ではないが、生徒との進路の会話に関わる（MVPでは専用画面なし）
- **期間**：4週間（2026-09-21 〜 締切 2026-10-18）

#### ペルソナ：美咲さん（チームC）

- 高校1年生。2年生で文理選択がある私立共学校（長野県・地方）。夏にソフトテニス部へ入部し部活が忙しい。趣味は推し活
- 家族：父（会社員）、母（パート）、弟（中学1年生）
- きっかけ：夏休みの課題「文理選択の前に、興味のある仕事を調べる」
- 状況：第二志望校に入学した挫折経験があり、目標を持って入学したが、どんな大学・職業があるのかイメージできない。本人も親も「知っている職業」の範囲でしか会話できず、「これでいいのか」と悶々としている。そこへ学校から「しごとみっけ」が提供された

#### 解決したい課題と理想状態

| 対象 | 課題 | 理想状態 |
| ---- | ---- | -------- |
| 生徒（美咲さん） | ・知っている職業の範囲でしか進路を考えられない<br>・気になる職業が、どの学問・学部・文理選択につながるか分からず、次の行動に結びつかない | 好き・興味・価値観を整理し、知らなかった職業に出会う。気になる職業と学問・学部・文理のつながりを理解し、文理選択や進路を自分で考える材料を得る |
| 親 | ・知っている職業の範囲でしか会話できない<br>・偏った知識・価値観でしかアドバイスできない | 偏った価値観に頼らず、子ども個々に合った視野を広げる助言ができる |
| 学校 | ・生徒個々の興味に合わせた進路支援の手段が不足<br>・進学実績を上げたいが有効な手段がない<br>・少子化で入学希望者が減少し、学校の魅力・実績向上が必要 | 生徒一人ひとりの興味・関心に応じた進路探索を支援し、職業と学問・文理のつながりを理解するきっかけを提供できる |

### 4. 業務フロー（As-Is / To-Be）

- **現在の業務（As-Is）**：
  - 文理選択の材料は学校の進路面談・パンフレット・自力の検索が中心。職業を知る機会が限られ、「知らない職業」に出会いにくい。
- **新システムでの業務フロー（To-Be）**：
  - **学校管理者**：seedで作成済みのアカウントでログイン（自己登録なし。#11で決定）→ 学校コードを生徒に共有 → 期間内に有料プランへ申込（Stripe Checkout）→ 契約中
  - **生徒**：学校コードとニックネームで開始（アカウント登録・ログインはない）→ ③好き・気になるカード選択（1〜3個）→ ④自分らしさチェック5問 → AIが「強みのタネ」3つを提示 → ⑤職業をスワイプで閲覧→ ⑥職業詳細（なぜあなたにつながる？／仕事内容／関連学問と文理）→ 職業一覧へ戻る
  - **職業の選び方**：好きなものタグ・特性タグと職業マスタのタグの一致度で機械的に候補を出す。AIは「強みの言語化」のみ担当。「なぜあなたにつながる？」もタグの一致からテンプレートで組み立て、AIは使わない（#30で決定）。

### 5. 機能要件

優先度：**M**=MVP必須 / **C**=対象外（今回やらない）。**最優先は生徒画面の完成度。** 以前 S（余裕があれば）だった機能は、工数を生徒画面に集中させるため **C（実施しない）** に変更した。

### 6. 非機能要件

| 項目 | 内容 |
| ---- | ---- |
| パフォーマンス | 通常画面 応答1秒以内（95%）。AI生成は10秒以内を目標、超過時はローディング表示 |
| 同時利用 | 1クラス〜学年単位（〜200人程度）が同時に操作しても劣化しない。**AI呼び出しがボトルネックになるためタイムアウトと固定文フォールバックを設ける（レート制限は余裕があれば追加）** |
| 可用性 | 授業時間内に使えること。稼働率99%を目標（MVPでは冗長化しない） |
| セキュリティ | TLS必須、学校管理者の認証は Firebase Authentication（パスワード管理は委託）、生徒はサーバー発行のセッショントークン（JWT）。Express はロール・学校IDで認可、OWASP Top 10対策、学校間のデータ分離（他校の生徒データを参照不可）、APIキー・Stripeシークレットはサーバー側のみ保持 |
| 個人情報 | **生徒の個人情報は預からない**（保持は学校に紐づくニックネームのみ）。学校管理者のメールのみ Firebase で保持。AIへ送るデータに氏名・メール・ニックネーム等を含めない。プライバシーポリシー・利用規約の整備が必要。AIサービスの学習利用設定を確認 |
| AIの出力制御 | 断定・進路の推奨（「向いている」「理系にすべき」）を出力しないようプロンプトとJSONスキーマで制約。不適切出力の簡易チェック |
| 対応端末 | 生徒：iOS Safari / Android Chrome（最新2バージョン）、幅360px〜。管理者：PC Chrome / Edge / Safari（最新2バージョン） |
| アクセシビリティ | 文字の読みやすさ（高校生向けの平易な表現）、色だけに依存しない選択状態表示 |
| 運用・保守 | 職業データはDBで管理し、コード変更なしで差し替え可能。無料枠中心でランニングコストを抑える |

> 運用・セキュリティ・ログの方針は、[`技術選定`](./技術選定.md)（リスクと対応）、[`API設計`](./API設計.md) の §6、[`README`](../README.md) の §6 に集約する（専用の運用設計・セキュリティ設計・ログ設計の文書は今回作成しない）。

### 8. データ要件

- **主なデータ項目**
  - 学校：学校名、学校コード（自動発行・一意）
  - 学校管理者：Firebase UID、学校ID、メール（ログインID）※パスワードは Firebase 側で管理し DB には持たない
  - 生徒：学校ID、ニックネーム（**メール・パスワードは持たない**）
  - 契約：学校ID、ステータス（無料体験中／契約中／無料体験終了／契約期限切れ）、無料体験終了日（登録日＋30日）、契約有効期限（決済日＋1年）、Stripe顧客ID／支払いID
  - 診断結果：生徒ID、選択した好きなものタグ、5問の回答、算出した特性、AIが生成した強みのタネ（JSON）、作成日時
  - ~~職業閲覧ログ（「知らなかった！」）~~ 今回は作らない
- **マスターデータ**
  - 好きなものタグ12件、特性タグ5件、質問5問、学問領域タグ22件（文理category付き）
  - 職業マスタ39件（現時点）：職業名、高校生向け分野、仕事内容、好きなものタグ、特性タグ、学問領域タグ、画像
  - 職業⇔タグ、職業⇔学問領域は多対多
- **保存期間・整合性**：
  - 契約終了・学校退会時の生徒データの扱い（削除／匿名化）：要確認
  - 診断結果は生徒（セッション）に紐づけて保存する。再診断しても**過去の診断は削除せず**、`created_at` が最新の1件を有効とする（一覧・再表示の画面は作らない）
  - 学校コードは重複不可

### 10. 制約事項・前提条件

- **期間**：4週間（〜2026-10-18）、5名。**フロント→API→DB接続とコア機能デモを最優先**とする。
- **スコープ外（今回やらない）**：サブドメイン取得、フロントの自動テスト（Playwright）、`openapi.yaml`、「知らなかった！」・結果の再表示・結果共有・契約切れの生徒制限、ロードマップ画面(⑧)、教員向け分析ダッシュボード、AIチャット、パスワード再設定の画面（Firebase の再設定メール機能は使えるが画面は作らない）、SSO/学校の一括生徒登録、多言語対応。
- **将来の拡張**：学校向けの集計・生徒の特定、スコープ外にした機能のバックログは [`将来の拡張`](./将来の拡張.md) に整理した。
- **企画理念による制約**：AIに進路の判断をさせない。職業に文理タグを直接付けない（学問領域経由で表示）。
- **データ準備の前提**：職業マスタ・学問領域タグはチームで整備済み（Googleスプレッドシート）。**職業画像はAIで制作中**。画像が間に合わない職業は絵文字で代替する（画面が崩れないこと）。
- **最優先事項**：**生徒画面の完成度**（7画面をスマホ実機で仕上げる）。工数の配分・削る順は [`マイルストーン`](./マイルストーン.md) を参照。
- **技術スタック**：[`技術選定`](./技術選定.md) を参照。
- **環境**：開発（ローカル）／本番（デモ用の公開環境）の2面。ステージングはMVPでは設けない。

### 13. 講師要件（MUST / ADVANCED）との対応

| 区分 | 要件 | 対応方針 | 状態 |
| ---- | ---- | -------- | ---- |
| MUST | 技術スタックはチームで決める | [`技術選定`](./技術選定.md) | 案あり |
| MUST | Webアプリ、フロント・バック分離 | Next.js（フロント専用）＋ Express（API） | 案あり |
| MUST | コンテナ利用 | Docker / Docker Compose（front, api, DB, Redis）。API は本番もコンテナ。**フロントの本番は Render（コンテナなし。当初は Vercel の予定で、コンテナ不要は講師確認済み）** | 案あり |
| MUST | キャッシュサーバー（Redis or Memcached） | Redis：**職業・質問・好きなものマスタのキャッシュのみ** | 案あり |
| MUST | 決済機能（Stripe等） | Stripe Checkout＋Webhook（FR-A04）。**優先度をSからMに格上げ** | 案あり |
| MUST | XSS / SQLインジェクション対策 | React エスケープ・CSP・helmet、Prisma パラメータ化、express-validator による入力検証 | 案あり |
| MUST | 単体テストのテストコード | Vitest / Supertest（マッチング、認証・認可、契約状態、Webhook 等） | 未着手 |
| MUST | テスト設計書・テストシナリオ | 別途作成（診断フロー、管理者フロー、決済、エラー系、スマホ実機） | 未着手 |
| MUST | 開発/本番でログ出し分け | pino を `NODE_ENV` で切替（開発：debug・整形／本番：info・JSON・個人情報マスク） | 案あり |
| ADVANCED | 本番デプロイ | Render（フロント・API） / Neon / Redis | 案あり |
| ADVANCED | LLM組み込み | OpenRouter経由（`openai/gpt-oss-120b`、強みのタネ生成） | 案あり |
| ADVANCED | プロンプトインジェクション対策 | 入力を選択肢IDのみに限定、出力のスキーマ検証、プロンプト分離（追加の対策は行わない） | 案あり |
| ADVANCED | フロントのテスト自動化 | **実施しない**（生徒フローはテストシナリオ＋スマホ実機確認で担保） | 対象外 |
| ADVANCED | サブドメイン取得 | **実施しない**（提供ドメインで HTTPS 化） | 対象外（講師に確認） |
| ADVANCED | HTTPSアクセス | ホスティングの自動証明書 | 案あり |

> 影響：FR-A04（Stripe）は必須なので優先度 M。ADVANCED まで狙うと工数が増えるため、マイルストーンでの優先順位を下記に定める。
> 優先順位：**生徒画面の完成度（P0）→ MUST の最小実装 → 本番デプロイ・HTTPS → LLM → プロンプトインジェクション対策（基本）**。フロント自動テスト・サブドメインは実施しない。
