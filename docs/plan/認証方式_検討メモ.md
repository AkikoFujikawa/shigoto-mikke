# 認証方式の検討メモ（チーム議論用）

## 1. 決めたいこと

1. 学校管理者の認証を何で実装するか
2. 生徒に認証（メール＋パスワード）を持たせるか

前提：講師の要件は「技術スタックは全レイヤ自由」。認証は MUST／ADVANCED に含まれない。

## 2. 現在の案と論点

| 論点 | 内容 |
| ---- | ---- |
| 学校管理者 | 契約・Stripe・学校コードを学校に紐づけるため**認証は必要** |
| 生徒 | 診断結果の保存・再表示、他生徒との分離のために認証が必要か？ |
| 方針との整合 | 以前の方針「教員は個人情報を預からない」と、生徒のメール収集が衝突する |
| 画面設計 | PDF の生徒「新規登録」「ログイン」画面が現案では存在する |

## 3. 選択肢

| 案 | 管理者 | 生徒 | 実装量 | 個人情報 | 主な欠点 |
| -- | ------ | ---- | ------ | -------- | -------- |
| A | Firebase Auth | Firebase Auth（メール＋パスワード） | 小 | 生徒メールを預かる | 学校への説明が必要。PDFの画面はそのまま |
| B（推奨） | Firebase Auth | 学校コード＋ニックネーム（匿名セッション） | 最小 | 預からない | 結果は同じ端末のみ。PDFの生徒画面を1画面に変更 |
| C | 自前（bcrypt＋JWT） | 自前（メール＋パスワード） | 大（+2〜3人日） | 生徒メールを預かる | セキュリティの実装責任が大きい |
| D | 自前 | 学校コード＋ニックネーム | 中 | 預からない | 管理者認証の自作が必要 |

## 4. 判断基準（チームで点をつける）

| 基準 | 重み | A | B | C | D |
| ---- | ---- | - | - | - | - |
| 5名・4週間で終わるか | 高 | | | | |
| 個人情報を預からない方針と合うか | 高 | | | | |
| セキュリティを担保できるか | 高 | | | | |
| 結果を再表示できる（美咲さんの体験） | 中 | | | | |
| 学校導入時に説明しやすいか | 中 | | | | |
| 画面設計（PDF）の変更が少ないか | 低 | | | | |

## 5. 話し合いで確認したい問い

1. 生徒は診断結果を**別の日・別の端末**でも見返す必要があるか？（ペルソナの美咲さんは、親と一緒に見ることもある）
2. 学校は生徒のメールアドレスを集めることを許容するか？（導入先の学校の声を想定して）
3. ニックネーム方式の場合、なりすましや他人の結果を見られる問題は許容できるか？（結果に個人を特定する情報は含まれない）
4. 別端末での再表示が必要なら、簡易 PIN（4桁）＋ニックネームで妥協できるか？
5. 認証にかける工数の上限は何人日か？（Stripe・Redis・テスト・デプロイが必須のため）
6. チームに Firebase の経験者はいるか？

## 6. 決まったら変更する箇所

- 要件定義：FR-S01・S02・S09、データ要件、セキュリティ要件、画面一覧（UI-S01・S02）、未決定事項1
- 技術選定：認証行、比較サマリ、リスク表
- 画面設計：生徒の新規登録・ログイン画面（B・D の場合は1画面に統合）
- 作業：Week1 の疎通確認の内容

## 7. 決定記録

- 決定日：2026-09-20（**暫定**。チームで確認して確定する）
- 決定案：**案B（学校コード＋ニックネーム）の最小構成**。生徒はアカウントを持たず、`POST /v1/students/session` でセッションJWTを受け取る。管理者は Firebase 認証
- 理由：生徒画面の完成度を最優先にするため。生徒側が入口1画面で済み（工数 約3人日、案Aは約6人日）、メール・パスワードを預からないため「教員は個人情報を預からない」方針とも整合する。「結果の再表示」を実施しないため、案Aの利点も小さい
- 将来の拡張：生徒の特定・学校向けの集計は [`将来の拡張`](./将来の拡張.md) にまとめた（今回は実施しない）
- 反対意見・懸念：別端末・別の日に結果を見返せない（同じタブの間のみ）。学校コードを知っていれば誰でも入れる（生徒データに個人情報がないため影響は小さい）。生徒の識別ができず、学校向けの利用状況の集計は将来の課題

## 8. スコープ変更（生徒画面を最優先）後の見方

生徒画面の完成度を最優先にする方針になったため、認証にかける工数は最小にしたい。

- **案B（学校コード＋ニックネーム）**：生徒側の認証が「学校コード検証＋セッション発行」だけになり、生徒画面が**入口1画面**で済む。実装は約3人日（案Aは約6人日）。個人情報も預からない。
- 案Aの利点（別端末で結果を見返せる）は、**「結果の再表示」を実施しない**方針になったため、価値が下がった（結果は同じ端末のセッション内で見られれば足りる）。
- **推奨は案B**（生徒画面の工数を確保できる）。ただし決定はチームで行う。
